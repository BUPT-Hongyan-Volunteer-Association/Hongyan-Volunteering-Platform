# 活动日程 · 模块设计

[业务需求](../../requirements/timeline.md) · [甘特图交互](../../../DESIGN.md) · [验收用例索引](../../../test/RTM.md)

## 1. 读取与合并模型

### 1.1 页集合

URL 保存范围、筛选、窗口、版本和选段。列表与时间轴共用 `createScheduleRange` 提交的页集合，详情从这些页里按活动和时段键定位。活动以编号、ID 排序。

### 1.2 一轮读取

| 入口 | 读取范围 |
| --- | --- |
| 初次进入、切换查询 | 立即清空旧结果，从第一页开始 |
| 加载更多 | 读取下一页，与已有页核对摘要 |
| 刷新、失败重试 | 从第一页重读到本次需要显示的末页 |
| URL 携带选段 | 从已读取范围向后查找，找到选中活动或读完窗口即停。重试从第一页重新定位 |

### 1.3 跨页一致性

每个分页请求在可重复读事务内筛选并计数。服务端在同一次扫描中按顺序计算所有匹配活动的日程字段摘要，包含活动身份、所选版本、时段、地点、负责人及展示状态。本人日程还纳入计算重叠所用的计划时段。请求时刻从摘要中排除，以便业务状态稳定时合并各页。成功响应通过 `X-Timeline-Range` 返回摘要。

客户端检查摘要、总数、连续页号、页大小、排序及每页的状态评估时刻。结果变化时从第一页重新读取目标范围，只在整轮校验通过后替换可见结果。末页收缩后丢弃新范围外的空页。连续两轮仍不一致时显示待刷新提示。旧服务端缺少响应头时，客户端重新读取整个范围，使用页结构校验，跨请求身份一致性依赖服务端提供摘要。

### 1.4 在途上限与查询切换

同一组件的读取轮次串行，每轮最多三个请求同时在途。切换查询立即使旧轮失效，旧轮停止领取新页，迟到的结果无法提交。页面可见时每 60 秒校准一次，聚焦或恢复可见时立即刷新；读取期间的刷新合并为一次待执行刷新。

### 1.5 失败与重试

单页网络失败保留上次成功提交的结果，记录本轮读取意图。重试整段读取，避免把旧前页和新后页拼接。当前查询任一页返回 403 时立即撤下旧数据，最终提示权限收回，重新读取从第一页开始。

### 1.6 详情返回与补页

每次成功读取后，如果 URL 仍有未定位的活动且后面还有页，则顺序补读。切换窗口后可再次定位同一活动。时段开始早于窗口结束时仍可能相交，补读成功后按实际分段匹配。

### 1.7 保持不变的窗口、刻度与分段规则

需求 F2 的规则不变，读取与合并模型建立在它们之上：

- 小时、日、周、月四种刻度共用一个日期窗口；窗口最长 31 日，超出由服务端拒绝（`apps/api/src/timeline/timeline.ts` 的 `window()`「日期窗口最长 31 天」）。
- 每项活动完整返回窗口内的全部分段，按真实起止时刻绘制；每周规则、排除日与补充时段由服务端展开（排除日取消当日全部例行时段，补充时段另成一段），本模块只按展开结果绘制。一次改期以「排除原日期 + 新增时段」表达，所以同一活动的时段键随版本变化，选中去留按 §2.2 判。
- 先筛选再按活动分页，`total` 为活动数；空页也返回统一的 `state_evaluated_at`——§1.1 与 §1.3 依赖这两条。
- 列表与时间轴共用同一次查询结果（§1.1 的 `rows`）。

## 2. 选中与失效判定

### 2.1 选中的来源

选中只由 URL 表达：`item` 是活动 ID，`slot` 是时段键。时段键由服务端生成，包含活动、展示版本与开始时刻，依据 `apps/api/src/timeline/timeline.ts`「occurrence_key: [view.id, view.schedule_revision, slot.starts_at].join('/'),」。页面不另存本地选中对象，刷新后按同一 URL 从最新结果重新解析。

- **`item` 没有 `slot`**：把该活动在当前结果里的第一个分段当作所选时段，判定在 `scheduleRange.ts` 的 `selection` computed（`const found` 在 `slot === undefined` 时取 `activity?.segments[0]`，否则按 `occurrence_key` 匹配所选键；`if (activity && found)` 收口为 `kept`），页面经 `SchedulePage.vue` 的 `segment`（`selection.value.kind === 'kept' ? selection.value.slot : undefined`）取用。这样的链接没有指认过具体时段，所以不会出现「所选时段…」两句；活动不在结果、或结果里没有该活动的分段，按 §2.2 第 4 种处置。

### 2.2 失效判定的结果与说明

一次**成功**的读取结束后，按最新结果判定。顺序固定：**先与响应中的时段键匹配，匹配不到再判窗口**。

1. 活动在、所选时段键在响应里匹配到：保留选中与详情；详情显示最新数据（标题、状态、分段随刷新更新）。匹配只认键、不看开始时刻——服务端只返回与窗口相交的分段（§1.7），开始时刻早于窗口首、结束在窗口内的分段同样在响应里。
2. 所选时段键匹配不到，且键的开始时刻早于窗口首或落在窗口结束及以后：清除选中，说明「所选时段已移出当前窗口」。响应就是与窗口相交的全部分段，键匹配不到说明这个时段不与当前窗口相交；活动是否已加载不改变这一结论。
3. 活动在、所选时段键匹配不到，且键的开始时刻落在本轮窗口之内：清除选中，说明「所选时段已随安排更新失效，已回到日程。」
4. 活动不在当前结果里，或结果里没有该活动的分段（筛选、窗口、待审状态、报名或交接变化），且没有 `slot` 或键的开始时刻在窗口内：清除选中，说明「所选活动已移出当前筛选。」

触发关系与 §1.4 一致：范围与展示版本切换在读取前静默清空选中，不进入以上四态；窗口与筛选变化保留选中，读取成功后按上面四态重判；读取失败的处置按 §1.5：已有可显示的页时保留选中与旧详情，只显示待刷新提示，不据此判失效；没有可显示的页时给「重新读取」入口，旧选中已随条件切换在读取前静默清空，没有旧详情可保留。

说明只写页面能观察到的依据：窗口来自 URL 的日期与刻度，开始时刻是时段键的第三段（§2.1）。键开始时刻在窗外而响应里没有它，说明当前窗口不包含这个时段；键在窗内却消失，而筛选都是活动级、不会只去掉一个时段，能解释的只剩安排本身变了。刷新、定时校准与审核返回都按这条判。

为什么第 2、3 种与第 4 种分开：前者判的是所选时段本身——键不与窗口相交是窗口移动，键在窗内消失是安排变了；后者判的是这条活动不在当前条件里。用同一句话会把页面并不知道的原因说成知道的。为什么一律清除而不是改选相邻时段：需求要求「已失效则清除并说明原因」，替用户挑一个替代时段等于替用户做选择。

**文案落点（三句）**：

- 权威落点：`DESIGN.md`「甘特图交互」——窗口外、窗口内消失、活动移出筛选三句的原文都在该节；改文案改那一处，本节四个状态引用的句子随同一次改动更新。
- 现成可用：提示通道 `selectionMessage`、清空动作 `clearSelection()`、渲染位置都在 `packages/ui/src/timeline/SchedulePage.vue` 的 `applySelection()`；三句共用这条通道与同一个渲染位置，不另起组件。
- 谁用：判定在 `scheduleRange.ts` 的 `SelectionState`；页面壳的 `applySelection()` 只按 `kind` 映射句子并清空 URL，不自己解析时段键。

## 3. 报名、交接与审核对可见范围的影响

- **不乐观增删**：报名状态、负责人成员关系、审核结论的变化只在下一次读取时体现。判据是变更稳定后同条件的服务端结果；本地预测会让页面自算集合变成第二个事实源。
- **mine**：录取后出现、退出待处理期间保留、退出获批后移出、恢复获批后重现，全部由服务端按有效录取关系判定；页面负责把刷新结果合并，并保留窗口、刻度、视图、筛选与其他仍可见活动。
- **managed**：负责人被移出单项活动后，该活动在下一轮读取中消失，`owner_options` 也随之更新；它若正被选中，按 §2.2 第 4 种清除并说明；其他活动与选中不受影响。
- **all + 只看待审**：审核处理后的活动不再满足待审筛选，下一轮读取把它移出结果；选中按 §2.2 第 4 种处理。
- **审核返回**：审核页的返回入口回填同一 URL（查询串不变），日程页重新挂载后执行一次初始读取，版本、待审状态与分段都取最新；页面不缓存跨页面结果。审核页的返回判定保持现状，依据 `apps/admin/src/activities/ReviewPage.vue`「return typeof origin === 'string' && /^\/schedule(?:\?|$)/.test(origin) ? origin : undefined;」。
