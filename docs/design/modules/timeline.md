## 1. 读取与合并模型

### 1.1 页集合

页面持一个页集合 `pages: TimelineActivityPage[]`，只保留**最近一次通过校验的页集合**。每一页带页号、页大小、该页活动、`total` 与 `state_evaluated_at`；页集合按页号排列，页号不重复。

- `rows` 由页集合平铺得到，列表与时间轴共用这一份（同一活动只出现一次）。
- `total` 取**页集合内各页一致的 `total`**：各页相等才有一个 total，任一页不等即判不一致并按 §1.3 重校准。
- `state_evaluated_at` 取第 1 页的值，用于进行中标记与时轴校准。
- 页大小固定 20（契约允许 1–100，默认 20）。
- 除第 1 页外不保留空页；第 1 页允许为空并携 `total=0` 与 `state_evaluated_at`。

### 1.2 一轮读取（pass）

一轮读取有明确的请求页号集合，按页号升序领取，同一轮内同一页号只领取一次：

| 意图 | 起始状态 | 请求页号 |
|---|---|---|
| 初次进入 | 清空页集合；选中由 URL 携带待判 | 第 1 页；URL 带 `item` 时按 §1.6 补读 |
| 刷新（聚焦／回页／60 秒定时） | 保留旧结果 | 已加载的全部页号，同轮取回 |
| 加载更多 | 保留旧结果 | 只取第 N+1 页，不重读第 1–N 页 |
| 失败重试 | 保留已验证前缀 | 从失败页续读到本轮目标页号 |
| 选中补读 | 保留旧结果 | 从第 N+1 页升序，找到所选活动即停 |

取回过程中不修改已提交的页集合；刷新与重试在取回结束、校验通过后整体替换；加载更多在追加第 N+1 页后对**合并后的页集合**整轮校验（§1.3）。

### 1.3 跨页一致性判据与重校准

判据只有一条：**页集合必须等于同一条件下服务端一次完整读取会给出的第 1–N 页**。契约没有快照令牌，所以改用「各页之间数据没有变化时本应同时成立」的性质来判定：

- 单个请求内计数与取页在同一个事务里完成，依据 `apps/api/src/activities/list.ts`「return db.$transaction(」「let total = derived ? 0 : await tx.activity.count({ where });」与「{ isolationLevel: 'RepeatableRead' }」。
- 分页的各页是各自独立的请求、各开各的事务，跨页之间没有共享快照；数据在两次请求之间变化时下列判据不成立，按本节整段重读处置。

判据五条：

1. 每页的 `page`、`page_size` 与请求一致；每个活动的 `state_evaluated_at` 等于所在页的值。
2. 把各页按页号串起来，`(activity_code, activity_id)` **严格递增**：无重复活动，无跨页回退。
3. 除末页外每页满页（`page_size` 项）。
4. 覆盖全集时（`N × page_size >= total`）活动数等于 `total`；除第 1 页外，已加载范围不超过覆盖所需页数（`(N-1) × page_size < total`，超出则截断）。
5. **页集合内各页的 `total` 相等**；加载更多时，新页的 `total` 必须等于已加载页的 `total`。

第 5 条是排序靠前项**移出**范围时最先出现的信号。分页按位置取：`skip` 是 `(page−1) × page_size`，移出 1 项后第 2 页给出的是新范围第 21–40 名，拼接仍严格递增、非末页满页，活动数也与末页 `total` 相等——其余四条都成立，只有跨页 `total` 不一致能暴露「旧第 21 项静默缺失、已移出项留在第 1 页」。一次移出多项时其余判据也可能同时不成立，第 5 条因此不承担唯一信号；任一条不成立都按下一段重读。范围在两次请求之间发生增删时各页 `total` 不等，重读后才自洽——这是判据的预期处置，不是误报。

任一条不成立即**整段重读**：从第 1 页把 1–N 全部重读一遍再校验；局部去重只会把缺口留下。一轮内最多两次整段读取，第二次仍不成立时保留上一次已验证的页集合，标为待刷新并给出重试入口。

读到空页（补读或加载更多）时的截断与重读按 §1.6 处置，截断后的页集合仍按本节判据校验。

- 为什么限制两次：数据集连续变化时再读几遍也证明不了什么，而无上限重启会把忙碌的数据集变成请求风暴；此时对用户有用的只有「上次结果 + 重试」。
- 为什么第二次通过就采纳：数据确实会变，刷新的目的就是采纳较新的真实结果；第二次能自洽就说明这几页之间数据没有变化。

### 1.4 在途上限与查询代际

- **在途上限 3**，由调用方显式传入，模块不设默认值。所有日程读取共用一个闸门：一轮读取、选中补读、加载更多、刷新、重试都在同一闸门内领取页号，因此任意时刻在途的日程请求不超过 3。
- 取 3 的理由：一屏可见约 3 页（每页 20 项），同一波取回即可填满视野；51 页刷新在 17 波内完成，峰值仍被钉死。
- **查询代际**：范围、展示版本、日期窗口、任一筛选项或页大小变化即代际加一，同时清空页集合。
- **选中只由范围与展示版本切换在读取前静默清空**（URL 去掉 `item`／`slot`）；窗口与筛选变化保留 URL 里的选中，读取成功后按 §2.2 重新判定。两个条件集不同，是因为前两者换掉了活动集合与展示版本，旧选中不再有意义；后两者只移动窗口或缩小结果，页面仍能观察到所选时段去留并给出对应说明。
- 旧代际的读取在**发起下一次请求之前**和**每次响应之后**检查代际，不匹配立即停止，已到响应丢弃。
- 在途请求不强制中止（请求层无取消能力时），但不再为旧查询发起新的页请求。
- 刷新触发只在一轮结束后开始；一轮进行中再次触发合并为一次待执行刷新。
- 组件卸载时推进代际，在途响应一律丢弃。

### 1.5 失败、重试与保留

- 读取失败保留上一次已验证的页集合与选中，记录**失败页号**与失败的意图；重试从该页续读到本轮目标页号，拼在已验证前缀之后，再整轮校验。续读不会掩盖缺口，因为最终仍走 §1.3 的判据。
- 403 表示权限收回：清空页集合、选中与详情，提示无权查看该范围，不保留旧结果。
- 没有可显示的页时给出重新读取入口；已有页时给出待刷新（刷新／重试失败）或未能加载更多（补页失败）的提示，按钮回到同一轮。

### 1.6 加载更多、补读与边界收缩

- 加载更多就是只追加第 N+1 页的一轮读取；追加后对合并后的页集合按 §1.3 整轮校验，第 5 条判据把新页与已加载页绑在同一个 `total` 上。
- 选中补读：`item` 不在已加载范围且还有更多页时，从第 N+1 页升序取页，**页预算 = 范围页数 `ceil(total / page_size)`**。早停条件四条：slot 的开始时刻在本轮窗口之外时直接按 §2.2 第 2 种处置、不发起任何补读请求；找到该活动即停；范围耗尽即停；403 或代际变化即停。一次挂载最多一次补读，请求全部经 §1.4 闸门。
- 为什么补读没有更小的页预算：结果按 `(activity_code, id)` 排序，页面无法从时段键推出目标页；任何小于范围的预算都会把「更深处」误判成「已移出」，而那是页面并不知道的原因（§2.2）。代价是请求数上界等于范围页数，只在 URL 带 `item` 时发生。
- 读到第 2 页及以后为空页：范围在读取期间收缩，按该页的 `total` 截断页集合（丢弃该空页及其后的页），再按 §1.3 判据校验，不把它当作「还有下一页」。截断不成立（已加载行越过新范围）时不得提交旧页集合：旧页集合仍以旧 `total` 自洽，提交它等于把越界行报成成功；此时转 §1.3 整段重读，由重读后的结果判定，仍不成立按 §1.3 的未稳定处理。加载更多与选中补读同此。

### 1.7 保持不变的窗口、刻度与分段规则

需求 F2 的规则不变，读取与合并模型建立在它们之上：

- 小时、日、周、月四种刻度共用一个日期窗口；窗口最长 31 日，超出由服务端拒绝（`apps/api/src/timeline/timeline.ts` 的 `window()`「日期窗口最长 31 天」）。
- 每项活动完整返回窗口内的全部分段，按真实起止时刻绘制；每周规则、排除日与补充时段由服务端展开（排除日取消当日全部例行时段，补充时段另成一段），本模块只按展开结果绘制。一次改期以「排除原日期 + 新增时段」表达，所以同一活动的时段键随版本变化，选中去留按 §2.2 判。
- 先筛选再按活动分页，`total` 为活动数；空页也返回统一的 `state_evaluated_at`——§1.1 与 §1.3 依赖这两条。
- 列表与时间轴共用同一次查询结果（§1.1 的 `rows`）。

## 2. 选中与失效判定

### 2.1 选中的来源

选中只由 URL 表达：`item` 是活动 ID，`slot` 是时段键。时段键由服务端生成，包含活动、展示版本与开始时刻，依据 `apps/api/src/timeline/timeline.ts`「occurrence_key: [view.id, view.schedule_revision, slot.starts_at].join('/'),」。页面不另存本地选中对象，刷新后按同一 URL 从最新结果重新解析。

- **`item` 没有 `slot`**：把该活动在当前结果里的第一个分段当作所选时段，判定在 `scheduleRange.ts` 的 `selection` computed（`if (slot === undefined) return { kind: 'kept', activity, slot: activity.segments[0] };`），页面经 `SchedulePage.vue` 的 `segment`（`selection.value.kind === 'kept' ? selection.value.slot : undefined`）取用。这样的链接没有指认过具体时段，所以不会出现「所选时段…」两句；活动不在结果、或结果里没有该活动的分段，按 §2.2 第 4 种处置。

### 2.2 失效判定的结果与说明

一次**成功**的读取结束后，按最新结果判定：

1. 活动在、所选时段键也在：保留选中与详情；详情显示最新数据（标题、状态、分段随刷新更新）。
2. 所选时段键的开始时刻落在本轮窗口之外：清除选中，说明「所选时段已移出当前窗口」。窗口判定先于活动查找，活动是否已加载、是否仍在结果里，都不改变这一判定。
3. 活动在、所选时段键不在，且键里的开始时刻落在本轮窗口之内：清除选中，说明「所选时段已随安排更新失效，已回到日程。」
4. 活动不在当前结果里，或结果里没有该活动的分段（筛选、窗口、待审状态、报名或交接变化），且没有 `slot` 或键的开始时刻在窗口内：清除选中，说明「所选活动已移出当前筛选。」

触发关系与 §1.4 一致：范围与展示版本切换在读取前静默清空选中，不进入以上四态；窗口与筛选变化保留选中，读取成功后按上面四态重判；读取失败时保留选中与旧详情，只显示待刷新提示，不据此判失效。

说明只写页面能观察到的依据：窗口来自 URL 的日期与刻度，开始时刻是时段键的第三段（§2.1）。键在窗外，说明当前窗口不包含这个时段；键在窗内却消失，而筛选都是活动级、不会只去掉一个时段，能解释的只剩安排本身变了。刷新、定时校准与审核返回都按这条判。

为什么第 2、3 种与第 4 种分开：前者判的是所选时段本身——键在窗外是窗口移动，键在窗内消失是安排变了；后者判的是这条活动不在当前条件里。用同一句话会把页面并不知道的原因说成知道的。为什么一律清除而不是改选相邻时段：需求要求「已失效则清除并说明原因」，替用户挑一个替代时段等于替用户做选择。

**文案落点（三句）**：

- 权威落点：`DESIGN.md`「甘特图交互」——窗口外、窗口内消失、活动移出筛选三句的原文都在该节；改文案改那一处，本节四个状态引用的句子随同一次改动更新。
- 现成可用：提示通道 `selectionMessage`、清空动作 `clearSelection()`、渲染位置都在 `packages/ui/src/timeline/SchedulePage.vue` 的 `applySelection()`；三句共用这条通道与同一个渲染位置，不另起组件。
- 谁用：判定在 `scheduleRange.ts` 的 `SelectionState`；页面壳的 `applySelection()` 只按 `kind` 映射句子并清空 URL，不自己解析时段键。

## 3. 报名、交接与审核对可见范围的影响

- **不乐观增删**：报名状态、负责人成员关系、审核结论的变化只在下一次读取时体现。判据是变更稳定后同条件的服务端结果；本地预测会让页面自算集合变成第二个事实源。
- **mine**：录取后出现、退出待处理期间保留、退出获批后移出、恢复获批后重现，全部由服务端按有效录取关系判定；页面负责把刷新结果合并，并保留窗口、刻度、视图、筛选与其他仍可见活动。
- **managed**：负责人被移出单项活动后，该活动在下一轮读取中消失，`owner_options` 也随之更新；它若正被选中，按 §2.2 第 4 种清除并说明；其他活动与选中不受影响。
- **all + 只看待审**：审核处理后的活动不再满足待审筛选，下一轮读取把它移出结果；选中按 §2.2 第 4 种处理。
- **审核返回**：审核页的返回入口回填同一 URL（查询串不变），日程页重新挂载后执行一次初始读取，版本、待审状态与分段都取最新；页面不缓存跨页面结果。审核页的返回判定保持现状，依据 `apps/admin/src/activities/ReviewPage.vue`「return typeof origin === 'string' && /^\/schedule(?:\?|$)/.test(origin) ? origin : undefined;」。

## 4. 接口契约

### 4.1 模块划分

`packages/ui/src/timeline/` 内的划分：

| 档 | 职责 |
|---|---|
| `SchedulePage.vue` | 页面壳：页头与视图切换、筛选字段与日期／刻度控件（`schedule-filters`、`schedule-controls`）、结果区与时段详情面板（`aside.schedule-detail`）、路由同步、错误与提示文案 |
| `scheduleRange.ts` | 读取与合并模型：页读取、校验、重校准、代际、在途闸门、选中解析 |
| `scheduleOptions.ts` | 纯取值：刻度箭头、状态／校区／负责人候选、展示版本项 |
| `window.ts` · `TimelineChart.vue` · `ScheduleDatePicker.vue` | 保持不变 |

为什么拆：读取与合并是一个有独立状态机的部件（代际、闸门、校验、重校准），留在页面壳里难以独立阅读与修改；取值是没有状态的纯函数，抽出来可单独验证。筛选控件与详情面板不拆：它们是纯展示块，外提只改文件体量、不改行为，而搬迁要动到页面模板里每一处绑定，回归面远大于收益；页面模板与样式的体量问题与读取模型无关，不由拆分读取模型解决。

### 4.2 `scheduleRange.ts`

```ts
export type RangeIntent =
  | { kind: 'initial' }
  | { kind: 'refresh' }
  | { kind: 'more' }
  | { kind: 'retry' }
  | { kind: 'focus'; activityId: string };

export type RangeOutcome =
  | { status: 'ok' }
  | { status: 'aborted' }
  | { status: 'failed'; failedPage: number; forbidden: boolean }
  | { status: 'unstable' };

export type SelectionState =
  | { kind: 'none' }
  | { kind: 'kept'; activity: TimelineActivity; slot: TimelineItem }
  | { kind: 'window-moved' }
  | { kind: 'schedule-updated' }
  | { kind: 'activity-missing' };

export interface RangeOptions {
  maxInFlight: number;
  pageSize: number;
  window: () => { from: string; to: string };
  selection: () => { item?: string; slot?: string };
}

export function createScheduleRange(
  read: (page: number) => Promise<TimelineActivityPage>,
  options: RangeOptions,
): {
  pages: ShallowRef<TimelineActivityPage[]>;
  rows: ComputedRef<TimelineActivity[]>;
  total: ComputedRef<number>;
  hasMore: ComputedRef<boolean>;
  evaluatedAt: ComputedRef<string>;
  running: Ref<boolean>;
  selection: ComputedRef<SelectionState>;
  run(intent: RangeIntent): Promise<RangeOutcome>;
  cancel(): void;
};
```

- `read` 由页面注入，负责把页号与当前查询变成 `GET /api/v1/timeline`；模块不拼 URL、不读路由。
- `maxInFlight`、`pageSize`、`window`、`selection` 必填且无默认值：前两者不是大于 0 的整数、后两者不是函数，都直接抛错并指名参数，不替调用方取值。
- `window` 是页面给的当前窗口取值函数，判失效时把时段键的开始时刻与它比较（§2.2）。
- 入参 `selection` 是页面注入的当前选中身份（`item` 是活动 ID，`slot` 是时段键），缺参即抛 `scheduleRange: 缺少 selection`，不做静默回退；判定用它取身份，不读路由。它与返回的 `selection` 同名不同义。
- 返回的 `selection` 是读取成功后的选中判定；页面只按 `kind` 映射说明文字与清空动作，不自己解析时段键。`item` 无 `slot` 时按 §2.1 取第一个分段，判定落在 `kept` 或 `activity-missing` 两种：没有键可比，不会判成窗口移动。
- `run` 同时只跑一轮；`initial` 会推进代际并取消旧轮。
- `run` 返回 `failed` 时页面据 `failedPage` 与 `forbidden` 决定文案与是否清空。

### 4.3 `scheduleOptions.ts`

```ts
export const revisionOptions: readonly { value: 'working' | 'published'; label: string }[];
export function unitArrows(unit: TimeUnit): [string, string];
export function statusOptionsFor(managed: boolean): { value: string; label: string }[];
export function campusOptionsFor(selected: string): { value: string; label: string }[];
export function ownerOptionsFor(
  lastPage: TimelineActivityPage | undefined,
  selected: string,
): { value: string; label: string }[];
```

全部是纯函数，只依赖入参，不读路由与全局状态；参数无默认值。

### 4.4 数据流

`route.query` → 页面派生范围、版本、窗口与筛选 → `range.run(intent)` → 模块经注入的 `read` 取页 → 校验与重校准 → 页集合 → `rows` → `SchedulePage.vue` 的结果区、筛选控件回显与时段详情面板 → 页面按 `RangeOutcome` 与 `selection` 决定提示与清空。

状态归属：URL 持条件与选中身份，模块持已加载范围、在途状态与选中判定，筛选与详情组件只持各自控件状态并向上发事件，服务端是唯一事实源。

## 5. 关键决策

| 决策 | 理由 |
|---|---|
| 位置分页 + 自校验整段重读，不引入游标 | 契约固定页号与页大小且不改契约；自校验用一次升序重读替代快照令牌，代价是最坏多一轮请求 |
| 一致性判据含「页集合各页 `total` 相等」 | 排序靠前项移出 1 项时其余判据全部通过，只有跨页 `total` 不一致能暴露缺口；各页是独立请求、没有共享快照，范围增删时它判不一致并触发整段重读，重读得到同一状态下的页集合 |
| 在途上限 3 | 一屏约 3 页，同一波填满视野；51 页刷新仍受限，峰值可断言 |
| 加载更多只追加第 N+1 页 | 全量重读已加载页会让深分页每次追加都付一遍范围成本；追加后仍整轮校验，缺口由 `total` 判据兜住 |
| 重校准最多两次 | 数据连续变化时多读无增益，无上限重启会放大请求；失败保留上次已验证结果并给重试 |
| 失败按页号续读，不整段重读 | 保留已有结果、代价最小；拼装后仍整轮校验，续读不会藏住缺口 |
| 补读页预算 = 范围页数，附四条早停 | 排序不含时段信息，任何更小的预算都会把「更深处」误判成「已移出」；窗口判定先于任何请求，把常见的窗口移动挡在补读之外 |
| 条件变化清空页集合、只有范围与版本切换清空选中 | 窗口与筛选只移动视野或缩小结果，页面仍能观察所选时段去留；范围与版本换掉活动集合与版本，旧选中不再有意义 |
| 失效说明按窗口内外分句 | 页面能观察的只有窗口与时段键：键在窗外是窗口移动，键在窗内消失是安排变了；合成一句就会说出页面并不知道的原因 |
| `item` 无 `slot` 取第一个分段、不产生时段说明 | 没有指认过时段，就不能说「所选时段」失效；沿用现有取值，链接行为不变 |
| 不乐观增删 | 判据是服务端结果，本地预测会造出第二个事实源 |
| 读取模型与取值拆出页面壳 | 读取与合并是有独立状态机的部件，留在页面里难读难改；取值是无状态的纯函数，抽出来可单独验证 |
| 筛选控件与详情面板留在页面壳内 | 纯展示块，外提只改文件体量、不改行为；搬迁要动到页面模板里每一处绑定，回归面远大于收益 |

## 6. UI 与交互决策

- 审核后返回：同一 URL、重新读取、页面顶部保留处理结果提示（现有的 `scheduleNotice` 机制，不改）。
- 选中失效的说明见 §2.2；三句提示语的权威落点是 `DESIGN.md`「甘特图交互」，§2.2 只定四个状态各说哪一句。
- 条件变化时清空页集合并显示「正在读取活动日程…」；范围与展示版本切换同时静默清空选中，窗口与筛选变化不动 URL 里的选中。刷新期间保留旧结果并标 `aria-busy`，不闪空态。
- 加载更多按钮在读取中禁用，范围耗尽后消失。
- 手机与桌面的筛选折叠、详情形态、时间轴绘制保持不变；筛选控件与详情面板留在页面壳内，其事件接口与可访问名称保持现状。
- 待审筛选下已处理的活动从结果移出，结果为空时显示空态「该窗口和筛选条件下没有活动」，不额外提示——它已不在当前筛选里。

## 7. 边界

- 不改 `GET /api/v1/timeline` 的契约与服务端范围语义，不新增查询参数；分页仍按 `activity_code` 与活动 ID 稳定排序。
- 不做游标分页、服务端快照令牌或版本号一致性接口；这些属于契约变更。
- 不做拖拽改期、时间条上审批、周期编辑器。
- 不做乐观本地增删，不做跨标签页同步，不加快轮询（仍是页面可见时每 60 秒、切回页面与聚焦时刷新）。
- 不做无限滚动或虚拟列表；「加载更多」保持显式。
- 不给补读设小于范围的页预算：那会把「更深处」说成「已移出」。
- 报名退出与活动交接的真实业务写入口不在本模块范围：两者用独立库预置关系验证，合入后再联调。

- **服务端契约与范围语义**：`apps/api/test/timeline.test.mjs`，独立库加真实 API，覆盖四种范围、版本、窗口、分页与分段展开。该套件作为服务端行为的回归基线保持全绿。
- **页面回归的索引**：`test/RTM.md` 的「日程」业务故事一节登记该故事的集成用例；标题、编号与「状态」列的写法按该档「使用约定」，本档不重述。其余业务故事尚未建立索引，登记在该索引文末的债务表。
- **页面回归的承载**：用例写在 `apps/api/test/pages.test.mjs` 的顶层用例里，真实 API 加浏览器加独立库夹具，覆盖审核返回、报名与交接、跨页重校准与深分页刷新上限；日程用例与既有用例同处该档，共享建库、起 API、两个预览服务与浏览器。

- **夹具**：`apps/api/test/timeline-fixture.mjs` 是可复用的数据集构造器：演示数据、深分页数据集、范围变化预置，以及同一项每周活动的获批／待审两版（改期以排除原日期加新增时段表达）。
